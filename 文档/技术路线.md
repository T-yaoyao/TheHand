# TheHand 技术路线

> 基于 Claude Code 源码架构分析，为 TheHand 项目制定的详细技术实现路线。

---

## 一、总体架构设计

### 1.1 分层架构（对标 Claude Code 六层架构）

Claude Code 的架构分为六层：CLI → TUI/REPL → Query/Agent Kernel → Tool/Permission → Memory/Persistence → MCP/Remote/Swarm。TheHand 借鉴这一分层思想，但根据自身"PM 驱动 + Web 应用"的定位做适配：

| Claude Code 层 | TheHand 对应层 | 说明 |
|---|---|---|
| CLI 启动层 | Web 前端入口 | PM 通过浏览器访问，不是命令行 |
| TUI/REPL 层 | 对话界面 + 状态流展示 | React 前端，展示需求状态机流转 |
| Query/Agent Kernel | Orchestrator 状态机调度 | 核心循环：接收 PM 输入 → 调度 Agent → 返回结果 |
| Tool/Permission | 工具管线 + 沙箱权限 | 文件读写、Shell 执行、Git 操作的安全管控 |
| Memory/Persistence | 业务上下文记忆 | 结构化需求 JSON、对话历史、执行记录 |
| MCP/Remote/Swarm | 项目适配层 | 可插拔的项目配置，类似 MCP 的"外部能力接入" |

### 1.2 核心设计原则（从 Claude Code 学到的）

| 原则 | Claude Code 实践 | TheHand 应用 |
|---|---|---|
| Fail-Closed 默认安全 | 工具默认不可并发、默认非只读 | 生成的代码默认需要验证，Git 操作默认在沙箱 |
| AsyncGenerator 驱动 | `query()` 是 AsyncGenerator，支持流式 UI | Orchestrator 用 SSE 流式推送状态给前端 |
| 文件系统即数据库 | 记忆全部存为 Markdown 文件 | 需求、对话、执行记录用文件 + SQLite 混合 |
| 分层组合 | 每层有清晰边界和可组合接口 | Agent/Skill/Tool 各层独立，通过标准接口通信 |
| 边界处缓存 | connectToServer memoize、auth cache | 项目上下文缓存、Skill 发现结果缓存 |

## 二、核心调度引擎（Orchestrator）

### 2.1 设计思路：借鉴 Claude Code 的 Query Loop

Claude Code 的核心是一个 `query()` AsyncGenerator 循环：

```
while(true) {
  → normalize messages
  → call Claude API (streaming)
  → extract tool_use blocks
  → runTools() (分区并发)
  → append tool_result to messages
  → compact check
  → if no tool_use: break
}
```

TheHand 的 Orchestrator 采用类似的循环模式，但增加**状态机驱动**和**PM 交互节点**：

```
while(requirement.status !== 'done' && requirement.status !== 'failed') {
  → 根据当前状态选择对应 Agent
  → Agent 执行（内部也是 LLM 调用循环）
  → 如果需要 PM 输入 → 暂停，等待 PM 回复（SSE 推送状态）
  → 更新 requirement.status
  → 持久化执行记录
}
```

### 2.2 状态机定义

```
┌──────────────────────────────────────────────────────────────┐
│                     需求状态机                                │
│                                                              │
│  idle ──→ clarifying ──→ clarified ──→ planning              │
│              │              │              │                  │
│              │ (3轮未澄清)   │              ▼                  │
│              │              │         plan-approved           │
│              ▼              │              │                  │
│           failed           │              ▼                  │
│              │              │         coding                  │
│              ▼              │              │                  │
│        (降级处理)           │              ▼                  │
│                            │         testing                 │
│                            │           │    │                │
│                            │      pass ▼    ▼ fail           │
│                            │         done   coding (重试)    │
│                            │                                  │
│                            └──→ plan-rejected ──→ idle (重来) │
└──────────────────────────────────────────────────────────────┘
```

### 2.3 Orchestrator 实现

```typescript
// core/orchestrator/orchestrator.ts

interface OrchestratorDeps {
  agentRunner: AgentRunner
  llmClient: LLMClient
  skillRegistry: SkillRegistry
  toolPipeline: ToolPipeline
  memoryManager: MemoryManager
  gitOps: GitOps
  eventEmitter: EventEmitter  // SSE 推送给前端
}

class Orchestrator {
  constructor(private deps: OrchestratorDeps) {}

  async *run(requirement: Requirement): AsyncGenerator<OrchestratorEvent> {
    // 清洁检查
    await this.deps.gitOps.cleanCheck()

    while (!this.isTerminal(requirement.status)) {
      const agent = this.selectAgent(requirement.status)

      yield { type: 'status-change', status: requirement.status, agent: agent.name }

      // 执行 Agent（内部可能多轮 LLM 调用）
      const result = await this.deps.agentRunner.run(agent, {
        requirement,
        context: await this.deps.memoryManager.getContext(requirement.id),
      })

      // 更新状态
      requirement = this.transition(requirement, result)

      // 持久化
      await this.deps.memoryManager.saveExecution(result)
      await this.persistRequirement(requirement)

      // 如果需要 PM 输入，暂停等待
      if (this.needsPMInput(requirement.status)) {
        yield { type: 'waiting-for-pm', requirement }
        const pmResponse = await this.waitForPMResponse(requirement.id)
        requirement = this.handlePMResponse(requirement, pmResponse)
      }
    }

    yield { type: 'completed', requirement }
  }

  private selectAgent(status: RequirementStatus): AgentDefinition {
    const mapping: Record<string, AgentDefinition> = {
      'clarifying': this.deps.agentRegistry.get('clarification'),
      'clarified':  this.deps.agentRegistry.get('plan'),
      'coding':     this.deps.agentRegistry.get('coding'),
      'testing':    this.deps.agentRegistry.get('test'),
    }
    return mapping[status]
  }
}
```

### 2.4 与 Claude Code Query Loop 的关键差异

| 维度 | Claude Code Query Loop | TheHand Orchestrator |
|---|---|---|
| 驱动方式 | 用户消息驱动，无限循环直到无 tool_use | 状态机驱动，有限状态自动流转 |
| 暂停机制 | 无暂停，连续运行 | 澄清阶段需等待 PM 回复（SSE 暂停） |
| Agent 选择 | 单一 query()，Agent 通过 AgentTool 切换 | 根据状态显式选择对应 Agent |
| 事件流 | AsyncGenerator<StreamEvent> | AsyncGenerator<OrchestratorEvent>，额外包含状态转换事件 |
| 错误处理 | 工具错误反馈给 LLM 重试 | 状态机降级策略（failed → 降级处理） |

## 三、Agent 体系

### 3.1 设计思路：借鉴 Claude Code 的 AgentDefinition

Claude Code 中，Agent 通过 `AgentDefinition` 类型定义，包含 `name`、`systemPrompt`、`tools`、`model` 等字段。`runAgent()` 包装了 `query()` 循环，为每个 Agent 注入专属的 system prompt 和工具集。

TheHand 采用类似的模式，但每个 Agent 有明确的输入输出契约：

### 3.2 Agent 基类定义

```typescript
// core/agents/base-agent.ts

interface AgentDefinition {
  name: string
  description: string
  systemPrompt: string | ((context: AgentContext) => string)
  tools: string[]              // 该 Agent 可用的工具名列表
  model?: string               // 可指定不同模型
  maxRounds?: number           // 最大 LLM 调用轮次
}

interface AgentContext {
  requirement: Requirement
  projectContext: ProjectContext
  memory: MemoryContext
}

interface AgentResult {
  agentName: string
  status: 'success' | 'failed' | 'needs-pm-input'
  output: any                  // 各 Agent 输出格式不同
  inputTokens: number
  outputTokens: number
  latencyMs: number
}
```

### 3.3 四个核心 Agent

#### 澄清 Agent（Clarification Agent）

```typescript
// core/agents/clarification-agent.ts

const clarificationAgent: AgentDefinition = {
  name: 'clarification',
  description: '识别 PM 模糊需求中的歧义，主动追问，输出结构化需求 JSON',
  systemPrompt: (ctx) => `
你是一个需求澄清专家。PM 会用自然语言描述需求，你需要：
1. 识别需求中的歧义和缺失信息
2. 主动追问（最多 3 轮）
3. 输出结构化需求 JSON

当前结构化需求状态：
${JSON.stringify(ctx.requirement.structuredRequirement, null, 2)}

项目上下文：
${JSON.stringify(ctx.projectContext.models, null, 2)}

输出格式：
{
  "type": "add_field | add_page | modify_api | delete_page | delete_field | ...",
  "entity": "Article | Comment | User | ...",
  "fields": [{ "name": "string", "type": "string", "description": "string" }],
  "scope": "frontend | backend | fullstack",
  "description": "string"
}
  `,
  tools: ['file-read'],  // 只需要读取项目文件，不需要写入
  maxRounds: 3,
}
```

**核心逻辑**：
- 每轮传给 LLM 的是「当前结构化需求 JSON + PM 新回复」（不传全量对话历史，避免 token 暴涨）
- 后续轮次额外注入「之前的澄清对话」（追问 + PM 回复），让 LLM 知道 PM 的回答是针对什么问题
- 轮次由 PM 回复数自动计算（currentRound = 1 + PM 回复数），传入 `runClarification` 的 `round` 参数
- 超过 3 轮自动进入降级策略：用已有信息 + 合理默认值生成"最可能的"结构化需求

**验证流水线**（三步阻塞式）：
1. **lint**（非阻塞）— ESLint 代码风格检查，warnings 不阻断流程

### 3.4 Agent 执行器（对标 Claude Code runAgent）

```typescript
// core/agents/agent-runner.ts

class AgentRunner {
  async run(agent: AgentDefinition, context: AgentContext): Promise<AgentResult> {
    const startTime = Date.now()
    const tools = this.filterToolsForAgent(agent)
    const systemPrompt = typeof agent.systemPrompt === 'function'
      ? agent.systemPrompt(context)
      : agent.systemPrompt

    let messages = [
      { role: 'system', content: systemPrompt },
      { role: 'user', content: this.buildUserMessage(context) },
    ]

    let totalInputTokens = 0
    let totalOutputTokens = 0
    let rounds = 0

    while (rounds < (agent.maxRounds ?? 10)) {
      rounds++

      // 调用 LLM（对标 Claude Code 的 API 调用）
      const response = await this.llmClient.chat(messages, {
        tools: tools.map(t => t.toSchema()),
      })

      totalInputTokens += response.usage.inputTokens
      totalOutputTokens += response.usage.outputTokens

      // 提取 tool_use（对标 Claude Code 的 extractToolUseBlocks）
      const toolUseBlocks = response.content.filter(b => b.type === 'tool_use')

      if (toolUseBlocks.length === 0) {
        // 没有工具调用，Agent 完成
        return {
          agentName: agent.name,
          status: 'success',
          output: this.parseOutput(response),
          inputTokens: totalInputTokens,
          outputTokens: totalOutputTokens,
          latencyMs: Date.now() - startTime,
        }
      }

      // 执行工具（对标 Claude Code 的 runTools）
      const toolResults = await this.toolPipeline.execute(toolUseBlocks, tools)
      messages.push({ role: 'assistant', content: response.content })
      messages.push({ role: 'user', content: toolResults })
    }

    return {
      agentName: agent.name,
      status: 'failed',
      output: { error: '超过最大轮次' },
      inputTokens: totalInputTokens,
      outputTokens: totalOutputTokens,
      latencyMs: Date.now() - startTime,
    }
  }

  // 对标 Claude Code 的 filterToolsForAgent
  private filterToolsForAgent(agent: AgentDefinition): Tool[] {
    return this.toolPool.filter(t => agent.tools.includes(t.name))
  }
}
```

## 四、Skill 机制

### 4.1 设计思路：借鉴 Claude Code 的 Skills 系统

Claude Code 的 Skills 核心设计：
- **Markdown + YAML frontmatter**：低门槛定义技能
- **三种来源**：File-based、Bundled、MCP
- **条件触发**：`paths` 字段订阅文件变更
- **内嵌 Shell**：`!`command`` 语法在 prompt 中嵌入实时系统状态
- **安全切断**：MCP 来源不执行 Shell

TheHand 的 Skill 系统借鉴这些设计，但更聚焦于**代码生成模式**的复用：

### 4.2 Skill 接口契约

```typescript
// core/skill-registry/types.ts

interface SkillDefinition {
  name: string                    // 技能名称
  description: string             // 描述
  canHandle: (requirement: StructuredRequirement) => boolean  // 是否能处理该需求
  execute: (requirement: StructuredRequirement, projectContext: ProjectContext) => Promise<SkillOutput[]>
  prompt?: string                 // 可选的 prompt 模板
  requiredFiles?: string[]        // 该 Skill 需要读取的文件模式
}

interface SkillOutput {
  path: string                    // 文件路径
  content: string                 // 文件完整内容
  summary: string                 // 变更摘要
}
```

### 4.3 Skill 文件格式（对标 Claude Code SKILL.md）

```markdown
# projects/conduit/skills/add-field/SKILL.md

---
name: add-field
description: 给 Sequelize 模型新增字段，并同步更新 API 和前端
canHandle: requirement.type === 'add_field'
---

## 代码模式

### 1. Model 层（Sequelize）

读取 `server/models/{Entity}.js`，在字段定义中新增：

```javascript
{fieldName}: {
  type: DataTypes.{fieldType},
  allowNull: true,
  defaultValue: {defaultValue}
}
```

### 2. API 层

读取 `server/routes/api/{entities}.js`，确保：
- 列表接口返回新字段
- 创建/更新接口接受新字段

### 3. 前端层

读取 `client/src/components/{Entity}Preview.js` 和 `{Entity}.js`，添加展示逻辑。

## 项目上下文

当前模型定义：

!`cat projects/conduit/context/routes.json`

**内嵌 Shell 执行**：`!`cat ...`` 在 Skill 加载时执行，把项目上下文注入 prompt。这直接借鉴了 Claude Code 的 `executeShellCommandsInPrompt()` 设计。

### 4.4 Skill 注册表

```typescript
// core/skill-registry/skill-registry.ts

class SkillRegistry {
  private skills: Map<string, SkillDefinition> = new Map()

  // 对标 Claude Code 的 getSkillDirCommands()
  async discover(projectDir: string): Promise<void> {
    const skillsDir = join(projectDir, 'skills')
    const entries = await fs.readdir(skillsDir, { withFileTypes: true })

    await Promise.all(
      entries.filter(e => e.isDirectory()).map(async (entry) => {
        const skillPath = join(skillsDir, entry.name, 'SKILL.md')
        if (await fileExists(skillPath)) {
          const skill = await this.loadSkill(skillPath)
          this.skills.set(skill.name, skill)
        }
      })
    )
  }

  // 对标 Claude Code 的 createSkillCommand()
  private async loadSkill(path: string): Promise<SkillDefinition> {
    const content = await fs.readFile(path, 'utf-8')
    const { frontmatter, body } = parseFrontmatter(content)

    // 执行内嵌 Shell（对标 executeShellCommandsInPrompt）
    const processedBody = await executeShellCommands(body)

    return {
      name: frontmatter.name,
      description: frontmatter.description,
      canHandle: this.buildCanHandle(frontmatter.canHandle),
      execute: this.buildExecutor(processedBody),
      prompt: processedBody,
    }
  }

  // 根据需求匹配 Skill
  match(requirement: StructuredRequirement): SkillDefinition | null {
    for (const skill of this.skills.values()) {
      if (skill.canHandle(requirement)) return skill
    }
    return null
  }
}
```

### 4.5 Skill vs Claude Code Skill 的差异

| 维度 | Claude Code Skill | TheHand Skill |
|---|---|---|
| 触发方式 | 用户 `/skill-name` 或条件触发（paths） | Agent 内部根据需求类型自动匹配 |
| 输出形式 | 注入 prompt 给模型 | 输出具体的文件修改内容 |

### 5.4 工具执行管线

```typescript
// core/tools/tool-pipeline.ts

class ToolPipeline {
  async execute(toolUseBlocks: ToolUseBlock[], availableTools: Tool[]): Promise<ToolResult[]> {
    // 对标 Claude Code 的 partitionToolCalls()
    const batches = this.partitionByConcurrency(toolUseBlocks, availableTools)

    const results: ToolResult[] = []

    for (const batch of batches) {
      if (batch.isConcurrent) {
        // 并发执行（对标 runToolsConcurrently）
        const batchResults = await Promise.all(
          batch.items.map(item => this.executeSingle(item, availableTools))
        )
        results.push(...batchResults)
      } else {
        // 串行执行（对标 runToolsSerially）
        for (const item of batch.items) {
          results.push(await this.executeSingle(item, availableTools))
        }
      }
    }

    return results
  }

  private async executeSingle(item: ToolUseBlock, tools: Tool[]): Promise<ToolResult> {
    const tool = tools.find(t => t.name === item.name)

    // 1. Schema 校验（对标 Zod safeParse）
    const parsed = tool.inputSchema.safeParse(item.input)
    if (!parsed.success) {
      return { type: 'error', content: `输入校验失败: ${parsed.error.message}` }
    }

    // 2. 语义校验（对标 validateInput）
    const semanticError = await this.validateSemantics(tool, parsed.data)
    if (semanticError) {
      return { type: 'error', content: semanticError }
    }

    // 3. 权限检查（对标 checkPermissions）
    if (!this.checkPermission(tool, parsed.data)) {
      return { type: 'error', content: '权限不足' }
    }

    // 4. 执行
    return await tool.call(parsed.data, this.context)
  }

  // 对标 Claude Code 的 partitionToolCalls()
  private partitionByConcurrency(blocks: ToolUseBlock[], tools: Tool[]): Batch[] {
    const batches: Batch[] = []
    let currentConcurrent: ToolUseBlock[] = []

    for (const block of blocks) {
      const tool = tools.find(t => t.name === block.name)
      if (tool?.isConcurrencySafe) {
        currentConcurrent.push(block)
      } else {
        if (currentConcurrent.length > 0) {
          batches.push({ isConcurrent: true, items: currentConcurrent })
          currentConcurrent = []
        }
        batches.push({ isConcurrent: false, items: [block] })
      }
    }

    if (currentConcurrent.length > 0) {
      batches.push({ isConcurrent: true, items: currentConcurrent })
    }

    return batches
  }
}
```

### 5.5 文件写入工具（核心安全设计）

```typescript
// core/tools/file-write-tool.ts

const fileWriteTool = buildTool({
  name: 'file-write',
  description: '将生成的代码写入 sandbox-repo 中的指定文件',
  isConcurrencySafe: false,  // 写操作不并发
  inputSchema: z.object({
    path: z.string(),
    content: z.string(),

  call: async (input, context) => {
    const fullPath = join(SANDBOX_REPO, input.path)

    // 安全检查：路径必须在 sandbox-repo 内（防止路径穿越）
    if (!fullPath.startsWith(SANDBOX_REPO)) {

    if (containsDangerousCode(input.content)) {

    // 备份原文件（用于回滚）
    const backup = await readFileIfExists(fullPath)
    await context.backupStore.save(input.path, backup)

    // 写入
    await fs.mkdirp(dirname(fullPath))
    await fs.writeFile(fullPath, input.content)

    return { type: 'success', content: `已写入 ${input.path}` }
  },

### 7.1 流程设计（对标 PRD 第八章）

```

    │
    ▼

    │
    ▼

    │
    ▼

    │  有无关变更 → 告警，等待 PM 确认
    ▼

    │  失败 → 自动 git checkout -- . 回滚 → 报错给 PM
    │  成功 ↓
    ▼
git add → git commit → 创建 PR
```

### 7.2 Git 操作封装

```typescript
// core/git-ops/repo-manager.ts

class RepoManager {
  constructor(private sandboxPath: string) {}

  // 清洁检查
  async cleanCheck(): Promise<CleanCheckResult> {
    const status = await this.exec('git status --porcelain')
    if (status.trim() === '') {
      return { clean: true }
    }

    // 尝试自动清理
    try {
      await this.exec('git checkout -- .')
      await this.exec('git clean -fd')
      return { clean: true, autoCleaned: true }
    } catch (e) {
      return { clean: false, error: '无法自动清理，请手动处理' }
    }
  }

  // Diff 检查（检测无关变更）
  async diffCheck(expectedFiles: string[]): Promise<DiffCheckResult> {
    const changedFiles = await this.getChangedFiles()
    const unexpectedFiles = changedFiles.filter(f => !expectedFiles.includes(f))

    if (unexpectedFiles.length > 0) {
      return {
        hasUnexpectedChanges: true,
        unexpectedFiles,
        message: `检测到预期外的文件变更: ${unexpectedFiles.join(', ')}`,
      }
    }
    return { hasUnexpectedChanges: false }
  }

  // 回滚
  async rollback(): Promise<void> {
    await this.exec('git checkout -- .')
    await this.exec('git clean -fd')
  }

  // 提交并创建 PR
  async commitAndCreatePR(message: string): Promise<string> {
    await this.exec('git add -A')
    await this.exec(`git commit -m "${message}"`)

    // 创建 PR（对标 Claude Code 的 gh pr create）
    const prUrl = await this.createPR(message)
    return prUrl
  }
}
```

### 7.3 回滚机制

| 场景 | 处理方式 |
|---|---|
| lint/测试失败 | 自动 `git checkout -- .` 回滚到写入前状态 |
| 写入过程中断 | 清洁检查阶段自动检测并 reset |
| PM 取消操作 | 回滚到最近一次干净状态 |
| Diff 检测到无关变更 | 告警，等待 PM 确认后决定继续或回滚 |

3. 三级验证通过：Lint + 单测 + 集成测试
4. 成功创建 PR
5. PM 可在 Web 界面完成全流程

---

## 十二、关键技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 状态机实现 | 自研状态机（不用 XState） | MVP 阶段状态简单，避免额外依赖 |
| 数据库 | SQLite（不用 PostgreSQL） | MVP 单用户串行，SQLite 够用，零配置 |
| LLM 调用 | 直接 HTTP 调用（不用 LangChain） | 需要精细控制 prompt 和 token，LangChain 太重 |
| 前端框架 | React 18 + Vite | 与 Conduit 项目技术栈一致 |
| SSE vs WebSocket | SSE（Server-Sent Events） | 单向推送够用，实现简单 |
| 代码生成方式 | 整体重写（不是 diff patch） | LLM 生成完整文件更可靠，避免 diff 应用失败 |
| Skill 定义 | Markdown + JSON Schema | 借鉴 Claude Code，低门槛 |

## 十三、风险与降级策略

| 风险 | 降级策略 |
|---|---|
| 模型生成代码无法通过 lint | 测试 Agent 自动重试（最多 3 次），失败后报错给 PM |
| 模型生成代码无法通过 build | build 阻塞，不提交代码，报错给 PM（build 拦截 JSX 扩展名、缺失引用等结构性错误） |
| 模型能力不足（结构化 JSON 输出不稳定） | 拆分 prompt 为更小的子任务；必要时在该环节使用更强模型 |
| 澄清 3 轮仍未澄清 | 降级策略：用已有信息 + 默认值生成"最可能的"需求，标注"系统推测" |
| GITHUB_TOKEN 缺失 | 提示 PM 配置，同时提供手动 git push 命令 |
| sandbox-repo 脏状态 | 自动 git checkout -- . 清理，失败则拒绝执行 |
| 写入后引入无关变更 | Diff 检查告警，等待 PM 确认 |

## 十五、删除操作级联清理优化

### 15.1 问题背景

PM 提出"删除关于我们页面跳转链接"，TheHand 只删除了导航栏入口，路由定义、import 语句、页面组件文件全部遗留。根因是整个 pipeline 没有"删除操作需要级联清理"的认知。

### 15.2 优化措施

| 阶段 | 改动 | 文件 |
|---|---|---|
| 澄清 | 新增 `delete_page`、`delete_field` 需求类型 | `prompts/clarification/v1.md` |
| 方案 | 新增级联清理规则：删除页面必须列出导航组件、路由文件、页面组件 | `prompts/plan/v1.md`、`core/src/agents/plan-agent.ts` |
| 编码 | 放宽"不做额外改动"限制；删除文件输出 `__DELETE__` 标记 | `prompts/coding/v1.md` |
| 执行 | Orchestrator 识别 `__DELETE__` 标记，调用 `fs.rm` 删除文件 | `core/src/orchestrator/orchestrator.ts` |

### 15.3 删除页面的标准文件清单

当需求为删除页面时，方案 agent 应至少列出以下文件：

| 文件 | 操作 |
|---|---|
| 导航组件（如 `Navbar.jsx`） | 修改：删除导航链接 |
| 路由文件（如 `main.jsx`） | 修改：删除 import + route 定义 |
| 页面组件（如 `About.jsx`） | 删除：content 为 `__DELETE__` |

## 十六、澄清 Agent 多轮对话机制优化

### 16.1 问题背景

PM 回复澄清问题后，orchestrator 重新运行时存在 3 个 bug：
1. **轮次跟踪缺失**：`runClarification()` 从未传入 `round` 参数，始终默认为 1，LLM 无法执行"最多 3 轮"约束
2. **LLM 缺少上下文**：重新运行时只拼接 PM 回复，没有提供上一轮追问了什么问题，导致 LLM 可能重复提问
3. **第 3 轮未强制输出**：round=3 时如果 LLM 返回追问而非 JSON，仍会被当作 needsMoreInfo 处理

### 16.2 修复措施

| 文件 | 改动 |
|------|------|
| `core/src/agents/clarification-agent.ts` | 扩展 `runClarification` 签名，新增 `previousQuestions`、`pmReplies` 参数；用户消息注入历史对话上下文；round>=3 时追加强制输出指令；`parseClarificationResponse` 在 round>=3 且 LLM 未返回 JSON 时兜底返回 `needsMoreInfo: false` + `isDefaulted: true` |
| `core/src/orchestrator/orchestrator.ts` | 从数据库加载对话历史，计算 `currentRound = 1 + PM 回复数`，提取 system 类型追问问题，传入 `runClarification` 的新参数 |
| `prompts/clarification/v1.md` | 规则追加："澄清最多 3 轮，第 3 轮必须输出结构化 JSON" |

### 16.3 数据流（修复后）

```
第 1 轮：PM 提交需求
  → pmInput = 原始需求文字, currentRound = 1, previousQuestions = []
  → LLM 返回追问问题 → needsMoreInfo=true
  → 保存 system 对话 + status='clarifying'

PM 回复
  → POST /api/conversations → 自动重新触发 orchestrator

第 2 轮：orchestrator 重新运行
  → pmInput = PM 回复文字, currentRound = 2
  → previousQuestions = [上轮追问问题], pmReplies = [PM 回复]
  → LLM 看到「之前追问了什么 + PM 怎么回答的」，继续判断
  → 如果信息完整 → needsMoreInfo=false → 进入方案阶段
  → 如果仍需追问 → needsMoreInfo=true → 继续第 3 轮

第 3 轮（最终轮）
  → round >= 3 → 用户消息追加"最后一轮"指令
  → parseClarificationResponse 强制返回 needsMoreInfo=false
```

## 十七、项目约束机制

### 17.1 问题背景

编码 agent 不了解目标项目的具体约定（路由注册方式、组件目录结构、可用依赖），导致：
- 创建了未被使用的路由文件（如 `routes/index.jsx`），而实际路由在 `main.jsx` 内联定义
- 在已有组件目录创建 `index.jsx` 覆盖了原始 `index.js` re-export
- 引入了未安装的 UI 库（如 antd）

### 17.2 修复措施

| 文件 | 改动 |
|------|------|
| `projects/conduit/project.json` | 新增 `constraints` 字段：routing、components、dependencies、modification |
| `core/src/types.ts` | `ProjectContext` 新增 `constraints?: Record<string, string>` |
| `core/src/memory/project-memory.ts` | 加载 `projectConfig.constraints` 到 context |
| `core/src/agents/plan-agent.ts` | systemPrompt 注入项目约束；规则追加路由注册和组件修改约束 |
| `prompts/coding/v1.md` | 规则追加："必须遵守项目约束"、"修改已有文件只改需要改的部分" |
