## 🎯 三、13 种状态定义与流转规则

### 3.1 状态机全状态表

| 状态 | 类型 | 说明 | 下一状态 | 暂停点 |
|------|------|------|----------|--------|
| **idle** | 初始 | 需求刚创建，等待启动 | clarifying | ❌ |
| **clarifying** | 运行中 | 正在澄清需求，AI 可能追问 | clarified / waiting-for-pm | ✅ |
| **clarified** | 中间态 | 需求已结构化完成 | planning | ❌ |
| **planning** | 运行中 | 正在生成技术方案 | plan-ready / failed | ❌ |
| **plan-ready** | **暂停点** | 方案生成完毕，等待 PM 审批 | plan-approved / plan-rejected | ✅ **关键暂停点1** |
| **plan-approved** | 中间态 | PM 已批准方案 | coding | ❌ |
| **plan-rejected** | 终态 | PM 拒绝方案 | - | ❌ |
| **coding** | 运行中 | 正在生成代码文件 | testing / failed | ❌ |
| **testing** | 运行中 | 正在运行 lint/build/test | diff-ready / failed | ❌ |
| **diff-ready** | **暂停点** | 代码生成+测试通过，等待 PM 确认变更 | committing / failed | ✅ **关键暂停点2** |
| **done** | 终态 | 全部完成，代码已提交 | - | ❌ |
| **failed** | 终态 | 流程中某环节失败 | - | ❌ |
| **reverted** | 终态 | 代码已回滚 | - | ❌ |

### 3.2 三大关键暂停点设计

TheHand 最核心的设计智慧：**在两个高决策点主动暂停，把控制权交还给 PM**

```
暂停点1: plan-ready
  ├─ 输出：文件变更清单 + 风险评估（置信度0-100 + 风险等级低/中/高）
  ├─ 输出：自然语言大白话摘要，非技术PM也能看懂
  └─ PM 可操作：确认 / 修改方案 / 终止流程

暂停点2: diff-ready
  ├─ 输出：完整 git diff 变更内容
  ├─ 输出：Diff 安全检查报告（检测无关变更）
  ├─ 输出：自动启动 Dev Server 后页面截图预览
  └─ PM 可操作：查看变更 / 确认提交 / 终止流程

暂停点3: waiting-for-pm (澄清阶段)
  ├─ 输出：AI 主动生成的追问问题列表
  └─ PM 可操作：回复问题 / 跳过使用默认值
```

## 🧠 四、Orchestrator 核心调度机制

### 4.1 主循环 AsyncGenerator 设计

```typescript
// orchestrator.ts 核心模式
async *run(requirement, projectId): AsyncGenerator<OrchestratorEvent> {
  // 全链路追踪初始化
  // 创建/复用沙箱
  
  // ── 状态跳转智能恢复 ──
  if (requirement.status === 'diff-ready') {
    yield* this.phaseCommit(...)  // 直接跳转到提交阶段
    return
  }
  if (requirement.status === 'plan-ready') {
    yield* this.phaseCoding(...)  // 直接跳转到编码阶段
    return
  }
  
  // 完整流水线：澄清 → 方案 → 编码 → 测试 → 提交
}
```

**断点续跑特性**：
- 任何暂停点中断后，下次启动自动从断点继续
- 沙箱不销毁，所有中间状态完整保留
- 无需从头重跑，极大节省 LLM Token 成本

### 4.2 事件驱动的 SSE 推送机制

所有状态变化通过 Server-Sent Events 实时推送到前端：

```typescript
type OrchestratorEvent =
  | { type: 'status-change'; status; agent }      // 状态变更
  | { type: 'executing'; phase; progress }        // 执行进度 0-100%
  | { type: 'waiting-for-pm'; questions }         // 等待PM输入
  | { type: 'plan-ready'; plan; riskAssessment }  // 方案就绪
  | { type: 'risk-assessed'; assessment }         // 风险评估结果
  | { type: 'test-result'; passed; details }       // 测试结果
  | { type: 'diff-ready'; diff; screenshot }      // Diff 就绪
  | { type: 'completed'; prUrl }                   // 全部完成
  | { type: 'failed'; error }                      // 流程失败
```

## 🛡️ 五、关键节点流转细节

### 5.1 澄清 Agent 流转（最多3轮）

```
PM 输入 "给文章加阅读时长"
        │
        ▼
  第1轮澄清
    ├─ 输入：PM 原始需求 + 项目上下文
    ├─ LLM 输出：追问问题（估算还是精确？显示在哪些页面？）
    └─ 状态 → clarifying → 暂停 → waiting-for-pm
        │
        ▼
  PM 回复 "估算的，都显示"
        │
        ▼
  第2轮澄清
    ├─ 输入：上轮中间JSON + PM新回复 + 历史追问
    ├─ LLM 输出：完整结构化需求 JSON
    └─ 状态 → clarified
        │
        ▼
  第3轮兜底（强制输出）
    └─ 若仍有歧义，自动填充合理默认值，标记 isDefaulted=true
```

### 5.2 方案 Agent 自愈重试机制（最多3轮）

```
开始生成方案
    │
    ▼
  第1轮尝试
    ├─ 正常 → 解析 FilePlan[] → 成功
    └─ 失败 → 记录错误信息
        │
        ▼
  第2轮重试
    ├─ 输入追加：上轮失败详情
    └─ 重新生成方案
        │
        ▼
  第3轮最后尝试
    ├─ 仍失败 → 记录 Lesson 到知识库
    └─ 状态 → failed
```

**删除操作特殊增强**：自动查询历史变更记录，确保级联清理所有相关文件。

### 5.3 编码 Agent + 测试 自愈循环（最多3轮）

```
开始编码
    │
    ▼
  第1轮生成代码
    ├─ 写入所有 plan 文件（100% 不丢文件兜底机制）
    └─ 运行测试：lint → build → 单测
        │
        ├─ 测试通过 → 进入 Diff 检查
        └─ 测试失败 → 记录错误详情
            │
            ▼
  第2轮重试
    ├─ 输入追加：历史失败教训 + 上轮测试错误
    └─ 重新生成代码
        │
        ▼
  第3轮最后尝试
    ├─ 仍失败 → 保存 Lesson 到知识库
    └─ 状态 → failed
```

**第一性原理绝对不丢文件机制**：
- 构建文件映射表，确保 plan 中所有文件 100% 被覆盖
- LLM 漏返回的文件，自动读取原始内容兜底
- 绝不出现 0 个有效文件的异常情况

### 5.4 沙箱生命周期管理

```
需求启动
    │
    ▼
  创建隔离沙箱（临时目录 /tmp/thehand-sandbox-*）
    ├─ 从 sandbox-repo 递归复制
    ├─ 排除 node_modules 后重新 npm install
    └─ 完全隔离，不污染源仓库
        │
        ├─ 到达 plan-ready 暂停点 → 沙箱保留不清理
        ├─ 到达 diff-ready 暂停点 → 沙箱保留不清理
        └─ 全部完成后 → 沙箱 cleanup
```

## 📈 六、增强特性全景

### 6.1 风险评估系统

自动对方案进行 0-100 分置信度评分：
- 风险等级：low / medium / high
- 自动判断是否可以 autoApprove 一键自动执行
- 高风险需求强制 PM 人工确认

### 6.2 全链路追踪

每个需求分配唯一 traceId，记录：
- 各阶段耗时
- Token 消耗统计
- 预估成本（元）
- 所有 Agent 执行记录

### 6.3 历史教训知识库（Lesson System）

```
任何环节失败 → 自动保存 Lesson
    ├─ phase: 失败阶段
    ├─ filePath: 关联文件
    ├─ errorSummary: 错误摘要
    └─ fixHint: 修复提示
下次同类需求编码时 → 自动注入历史教训，避免重复踩坑
```

### 6.4 Diff 安全检查

对比生成代码与原始文件：
- 检测是否引入无关变更
- 标记意外修改的文件
- 确保只修改方案中明确列出的文件

### 6.5 页面自动截图预览

代码生成后自动：
1. 启动 Dev Server
2. 智能从方案中提取路由
3. 访问对应页面截图
4. PM 无需本地启动项目即可预览效果

## 💾 七、数据库持久化模型

```
requirements (需求主表)

  ├─ plan (JSON)
  ├─ confidence_score, risk_level

  ├─ requirement_id
  ├─ role: pm / system
  ├─ content, round

  ├─ requirement_id
  ├─ agent, skill
  ├─ input_tokens, output_tokens

  └─ 历史失败记录，用于自愈

change_history (变更历史)
  └─ 所有文件修改轨迹
```

## 🎯 八、核心设计哲学总结

| 设计原则 | 实现方式 | 价值 |
|----------|----------|------|
| **状态机驱动** | 13种明确定义状态，无模糊中间态 | 流程完全可预测，无死锁 |
| **主动暂停点** | plan-ready + diff-ready 两处关键决策点交还给PM | AI 做执行，人做决策 |
| **断点续跑** | 沙箱不销毁，状态持久化 | 绝不从头重跑，节省成本 |
| **自愈重试** | 每阶段最多3轮重试，自动注入错误上下文 | 大幅提升端到端成功率 |
| **绝对不丢** | 文件映射兜底机制 | 极端情况下也不会丢失任何计划中的文件 |
| **全容错增强** | 所有增强功能（追踪/评估/检查）try-catch 包裹 | 增强功能失败绝不阻塞主流程 |
| **Skill 注册制** | 可插拔 Skill 体系 | 新增需求模式零核心代码改动 |

---

> **TheHand 本质：一个由状态机严格控制的、在两个关键节点主动把控制权交还给人类 PM 的、支持断点续跑和自愈重试的 AI 驱动全自动化交付流水线。**
