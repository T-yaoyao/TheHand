# 澄清阶段：如何稳定「看到追问」

澄清是否出现**取决于 LLM 是否调用** `ask_for_clarification`，或在它**错误地** `submit_requirement` 后由**校验**转成追问。下面按「更容易触发」排序，在 **Conduit** 示例项目（含 `Article` / `User` / `Comment` / `Tag` 模型）下新建需求 → **运行流水线**，将 `pm_input` 设为下列之一即可反复试。

## 推荐复制粘贴（中文）

### 1. 几乎无信息（优先试）

```text
加字段。
```

模型若仍硬提交，常会带上不合法或缺 `fields` 的结构，下一轮会走**校验失败追问**或进入 `needs-confirmation`。

### 2. 缺实体、多实体都可解释

```text
列表里那一列显示不对，改一下，要和后台一致。
```

不说哪个列表（文章列表？用户列表？）、「一列」指哪一列、「一致」指同步哪种数据源。

### 3. 跨实体歧义

```text
作者旁边加个关注按钮，点了要能取消关注。
```

「作者」可能是 `Article` 作者，也可能是 `User` 个人页；是否动 `Article` / `User` 模型与 API 未说明。

### 4. 像加字段但不给名称与类型

```text
User 那边要存一个新东西，表单里也要能编辑，你看着办。
```

若模型选成 `add_field` 却未填 `fields`，会触发**结构化校验**后的追问（与主动 `ask_for_clarification` 一样会停在 `waiting-for-pm`）。

### 5. 范围含糊

```text
标签相关功能优化一下，前后端都看看。
```

未说明是 `Tag` 实体哪条路径、优化指性能、交互还是接口契约。

## 若仍然「一闪就澄清完成」

1. 确认跑的是**带真实 LLM** 的后端（`LLMClient` 会走 `chat` + tools）；本地 mock 若恒返回 `submit_requirement` 则看不到追问。  
2. 换用**更弱或更守规矩**的模型时，`ask_for_clarification` 命中率通常更高。  
3. 用例 **1 / 4** 最容易在「误提交」后靠 **validateRequirement** 拉回追问。  
4. 进入 `waiting-for-pm` 后，在 UI 里**故意简短乱答**再运行，可进入第 2、3 轮澄清，更容易看到多轮追问。
